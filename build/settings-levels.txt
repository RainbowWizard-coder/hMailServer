# The LEVELS MARK of every hm_settings property this build seeds or ensures - the
# deepest level the setting may be set at (one value, three levels, 23 September
# 2026; hmailserver/docs/SettingLevels.md has the rule and the whole inventory):
#   server        set for the whole server only;
#   domain        a domain may hold its own value, which wins over the server's;
#   account       an account may hold its own as well, which wins over both.
#
# build/generate-settings-defaults.py carries the mark into SettingsDefaults.h as
# each row's Levels and refuses to write the header when a property has none;
# build/check-settings-rows.py refuses a property of SettingsDefaults.h that is
# not listed here; build/check-setting-levels.py holds every property marked
# domain or account to a row of Application/EffectiveSetting's table - which is
# where the name REST, COM and hmctl use for it is given - and every row of that
# table whose server level is a property back to its mark here.
#
# The rule the marks follow: a setting about one mailbox - what the account is
# offered, what it may keep, how long, how much - reaches the account; a listener,
# a directory, the database, TLS, the delivery queue, a cache, the anti-spam and
# anti-virus engines and every setting that decides for the whole server before
# any account is known is server. The document says, name by name, why the ones
# about a mailbox that stay server do.
#
# One "name levels" per line, the name as the property is spelled.
