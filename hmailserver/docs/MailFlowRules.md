# Mail flow rules

The rules the server runs on every message, before delivery - Exchange's transport rules, Google's routing - and where they live.

## Three collections

| Collection | Where | Runs for |
| --- | --- | --- |
| The server's (`Application.Rules`, `/api/v1/rules`, the Control Panel's Rules page, the Deck's) | `hm_rules` with no account and no domain | every message, first |
| A domain's (`Domain.Rules`, `/api/v1/domains/{name}/rules`, the same pages with the domain chosen at the top) | `hm_rules` with `ruledomainid` (schema 6063) | every message with a recipient in the domain or a sender it hosts, after the server's - which is how a domain administrator has rules of their own: a domain-restricted key reaches its domain's rules and no other's. How far they reach is under *A domain's rules and other domains' mail* below |
| An account's (`Account.Rules`, `/api/v1/accounts/{address}/rules`) | `hm_rules` with the account | that account's mail, at local delivery |

All three run in `SMTPDeliverer` on every delivery attempt, after virus scanning and before DKIM signing and the split between local and external delivery, with the same conditions and actions. A pass that repeats an attempt because this server's own outbound shaping held it without counting a try ([OutboundShaping.md](OutboundShaping.md)) runs them again, but does not forward, copy, reply or call a script function again: that attempt already did, and what a script function does - it may send mail - cannot be known. An account's own rules are not affected by this: they run once for their recipient, when its copy is stored, whichever pass that is - and so does their warn_sender, which the server's and the domains' rules send once per message.

## A domain's rules and other domains' mail

Since 26 September 2026 a domain's rules act only on what is that domain's:

* **The sending domain's rules act on the whole message**: the domain of the account that submitted it (SMTP `AUTH`, the webmail, a scheduled send), and the envelope sender's domain when that is vouched for - its account submitted the message, or DMARC passed for the domain on mail from outside - or when the message reaches no other domain's mailboxes (an application relaying from the domain's own network). An envelope sender nobody vouched for does not choose a domain's rules for mail to another domain's mailboxes.
* **A recipient domain's rules act on the whole message when every recipient is its own.** When the message also goes to recipients outside the domain, they act on the domain's own recipients only: a delete or a reject takes those recipients off the message, and a quarantine keeps a copy for them under the rule's name first, while the rest of the message goes on; a copy goes to those recipients only; a header, a disclaimer, a script function, a route, a bound address and required TLS are not applied, since they would change the message for everybody; and a reject is met at delivery rather than at the SMTP session, whose one answer is for every recipient - a sender this server hosts is mailed a notice naming the recipients the rule refused and saying the others were not affected (an outside sender is told nothing, as for every notice).

Until then every recipient domain's rules, and the rules of the domain an unauthenticated `MAIL FROM` named, acted on the whole message, so one tenant's delete, reject, header or route reached another tenant's recipients.

## Conditions

From, To, CC, Subject, body, size, the recipient list, delivery attempts, any named header, and - since 17 September 2026 - **the attachment name** (`attachment_name`): every attachment's file name, `;` between them, so `contains .exe`, a wildcard `*.zip` or a regular expression reads as "any attachment is". Matched by equals, contains, their negations, less or greater, wildcard or regular expression, all or any.

Four more, in the same list shape, for the outbound content policy ([OutboundContentPolicy.md](OutboundContentPolicy.md)): **sensitive content** (`sensitive_content`: the detectors that found something in the readable text - `card_number`, `iban`, `account_number`), **attachment type** (`attachment_type`: every attachment's type by its first bytes, not its name), **external recipients** (`external_recipient`: every recipient this server does not host) and **readable text** (`content`: the plain and HTML parts and every attachment whose bytes are text, for a pattern of the rule's own).

## Actions

Delete, forward, reply, move to a folder, set a header, send using a route, create a copy, bind to an address, run a script function, stop - and four more:

* **Add a disclaimer** (`add_disclaimer`, `body`): the text appended to the message's plain and HTML parts when the rule matches, with `X-hMailServer-Disclaimer` naming the rule; the domain disclaimer stays the unconditional footer it was.
* **Reject with a text** (`reject`, `value`): the SMTP session answers `550 5.7.1` with the text **before the message is accepted**, where the sender is still there to be told - the server's rules, and those of every domain whose rules act on the whole message (below), are asked at the end of DATA, with the message parsed for the match only when one of them has a reject action at all, and the webmail's send route asks the same rules before it queues and answers `403`, code `policy_rejected`, with the text. A message that reached delivery another way is dropped, as a delete is, with the rule named in the log, and a sender this server hosts is mailed a notice saying it was not sent ([OutboundContentPolicy.md](OutboundContentPolicy.md)). The text is one line: a control character in it, or in the rule's name, is refused over REST.
* **Require TLS** (`require_tls`): every external delivery of the message needs STARTTLS, as a remote domain policy would require it; a destination that offers none is deferred with a reason naming the rule, and the message is not sent in the clear.
* **Quarantine** (`quarantine`): the message is held in the quarantine under `Rule: <name>` rather than delivered, for an administrator to release or delete; a quarantine that could not store it delivers the message rather than lose it, and says so in the error log.
* **Warn the sender** (`warn_sender`, `value`): the message goes where the rule's other actions send it, and a sender this server hosts is mailed a notice naming the rule, with the action's text, from the postmaster of the rule owner's domain - the account's, for an account's rule, and the domain's, for a domain's; for a server rule, the server's default domain when one is set and hosted here, else the domain the message was addressed to, else the sender's own - signed as that domain and marked auto-generated; an outside sender gets nothing, since that would be backscatter ([OutboundContentPolicy.md](OutboundContentPolicy.md)).

A reject with no text of its own names the rule in its 550, since 17 September 2026.

**Run a script function** (`script_function`) names a function of the event script ([EventScripts.md](EventScripts.md)) by its plain name - ASCII letters, digits, `_` and `$`, not starting with a digit, at most 255 characters - the only name the server runs. Since 12 October 2026 a missing name, or one that is not plain, is refused when the rule is saved (COM's `RuleAction.Save` and `Rule.Save`, the REST routes), for a rule of every owner, with the reason; until then COM stored any name and the REST routes any but an empty one, and the server refused it each time the rule fired - HM5018 on Windows, a Script Error line on Linux - which is still what becomes of one stored before, or restored from a backup.

### Who a rule may speak for

A domain's rules are saved by its administrator as well as by the server's, and an account may change its own over COM, signed in as itself. Which collection a rule is in is recorded; who saved it is not. So since 7 October 2026 two actions are held to the collection:

* **Set a header** may set `From`, `Sender`, `Resent-From`, `Resent-Sender` or `DKIM-Signature` - the fields that say who wrote or sent a message, and the signature it came with - in **the server's rules alone**, which only the server administrator saves. A domain's or an account's rule that names one, in any case and with blanks around it, is refused when it is saved (COM's `Rule.Save` and `RuleAction.Save`, the REST routes), whoever saves it, and says why; to set one, make the rule a server rule with a condition on the domain. A forward, a copy or a reply would otherwise go out in the name it wrote, and the server signs a message as the domain its `From` names ([SendAs.md](SendAs.md)). `Reply-To`, which names no sender, may be set by any rule.
* **Reply** is sent only from an address the rule's owner may send as: for an account's rule, an address the account may send as - its own, an alias of it, a mailbox that granted it the post right, an address it proved or a masked address of its own, the rule authenticated SMTP and the webmail's send apply ([SendAs.md](SendAs.md)); for a domain's rule, an address of that domain or of one of its domain aliases; for a server rule, any. The address must be one email address. Anything else is refused when it is saved, whoever saves it - an account's rule the server administrator saves is held to the account's addresses too, so that what is saved is what is sent. The reply's name is written as one quoted name before the address, so that a name holding a comma or an address adds no address to the `From` (until 7 October 2026 it was written as it stood). A reply from no address - the null sender - has the name before an empty `<>`, and a name with an `@` in it is left out, since the server's own reader would take it for the address and sign the reply as its domain.

An action stored before 7 October 2026 that these refuse - or restored from a backup since - is not taken at delivery, and the application log says so (`RuleApplier: the Set header value action of rule ...` or `the Reply action of rule ...`, with the reason); the rule's other actions are taken.

`Rule.Save` over COM writes every action of the rule, and holds one to these checks, and a Run script function action to its name, only where it changes it: a new action, one changed in any field or made another type, and every action of a rule moved to another account. A rule holding an action stored before them, restored from a backup or written to the table is changed around it as any other - a criterion or another action added or removed, as the Control Panel stores each before it saves the rule, an action moved up or down, that one too, the rule renamed or switched off - and the action is left as it is, still not taken. `RuleAction.Save` holds the action it saves whether or not it changes it, so the Control Panel's action dialog tells of such an action as refused, with the reason, until it is corrected; `RuleAction.MoveUp` and `MoveDown` store the places they give it and the action it passes, and the Control Panel's Move up and Move down then save the rule, not the action. From 7 October to 13 October 2026 every such save of a rule holding a Set header value or a Reply action stored so was refused, and the Control Panel told of the part it had stored already as not saved, stored it again at each retry, and left delivery with the rule as it had been; and its Move up and Move down, which asked `RuleAction.Save` of the action moved before they saved the rule, stored the move of such an action itself and told of it as refused, at each click.

## A message over 80 MB

The server reads a message whole up to 80 MB (`MessageData::MaxParseBytes`). The SMTP session takes a larger one only where its message size limit was raised past that (20 MB by default); an external account's fetch is held to no size limit, so it takes one whatever the setting; the webmail's send, held to 16 MB a request, never does. Since 13 October 2026 the rules read such a message's **header alone** - its end is looked for in the first 10 MB - and leave the body where it is, unread (upstream hMailServer #683 and #686, taken for the paths this section names and no others):

* **Conditions** on From, To, CC, Subject, a named header, the size, the recipient list, the delivery attempts and the external recipients are evaluated as for any message. The five that need the body - the body, the attachment name, the attachment type, sensitive content and readable text - **do not match**, whichever way round they are phrased, as for a sealed message ([SealedMail.md](SealedMail.md)): "does not contain" would otherwise match every such message. The rule's other conditions are still evaluated, and the application log says so once per rule per message (`RuleApplier - Message ... is larger than the 80 MB a message is read whole at, so only its header was read: the criterion of rule "..." that needs its body or its attachments could not be evaluated and did not match.`). A reject is asked at the SMTP session on the same terms (the webmail's send route asks the same rules, but never of a message this large).
* **Actions** that change the header - set a header, and the rule-loop count and `X-CopyRule` a forward and a copy write on their copy - write it with the body copied behind it from the file byte for byte, in pieces and never whole in memory, into a file beside the message that is renamed over it (a message an object store holds is handed over whole in memory, and written from there). A forward, a copy, a reply and a notice to the sender read the loop count from the header (a reply and a notice `Auto-Submitted` as well), so a forwarding loop of such a message ends at the rule loop limit. **Add a disclaimer** is not appended - finding the text part to append to means reading the whole message, and appending blind would land after a multipart message's closing boundary or inside an encoded part - and the log says so (`DisclaimerAdder - Message ... so the disclaimer of rule ... was not appended`); the message is delivered as it was sent. **Run script function** is not run on such a message: a script reads the message through the COM API's `Message`, which does not read one over 80 MB - its `Subject`, its other header fields and its body would read as empty, though the rule matched on them, and its `Save` would be refused (HM6010) - so the function is skipped, the log says so (`RuleApplier - Message ... so the script function ... of rule "..." was not run`), and the rule's other actions are taken. A message that a function makes larger than 80 MB - by adding an attachment - is read again header only after it has run, so that the rules after it still have its header.

The same header-only read serves an account's forward and a Sieve redirect (the loop count), a bounce (`Auto-Submitted` and the loop count, and the report carries the header), an inbound webhook's return of a kept message to its sender (`Auto-Submitted` and the loop count), the spam headers of a message the SMTP session or an external account's fetch marks as spam (`X-hMailServer-Spam`, the reasons and the subject's tag, written as the header is) and their removal from the copy of an account with spam filtering off, with a mark threshold of 0 or with the sender on its allow list ([SenderListsAndDigests.md](SenderListsAndDigests.md)), and the signature and the domain's disclaimer, which are not appended to such a message either ([DomainTransforms.md](DomainTransforms.md)). Everything else that reads messages - the virus scanner, the sandbox, the indexer, IMAP SEARCH, the REST routes, a distribution list's posting, the COM API's `Message` that an event's script reads (a rule's function is not run, above), the marking of a blocked sender's copy (HM6747) and the score an account's own spam thresholds read - refuses a message over 80 MB as it always has.

Until 13 October 2026 none of these read such a message at all: no rule ran on it (HM6040), a forward or a redirect read its loop count as 0 and could not write it (HM6010 at every hop, so two accounts forwarding to each other passed it back and forth without end), a bounce of it read neither the count nor `Auto-Submitted`, the spam headers of one marked as spam could not be written (HM6010), nor the copy of an account that asks for it unmarked be read to take them off (HM6351), and the footers were left off without a word.

Three errors are new. **HM7841** (Medium): a message over 80 MB whose header has no end in its first 10 MB, or holds a field the parser refuses, or whose file could not be opened or read (held open by another program, say) - it is not loaded, as before, and nothing is written over it. **HM7842** (High): when the header was written back, the message file was shorter than when it was read, or a read or the write failed - the message is left as it was. **HM7840** (High): a change to the body of a message read header only, which nothing on the server's own paths makes - refused, and the message left as it was.
