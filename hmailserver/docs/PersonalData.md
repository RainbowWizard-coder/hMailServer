# A person's data: the export and the erasure

The two halves of a data-subject request, as the server does them.

## Everything the server holds, as one archive

`Account.ExportArchive(file)` over COM, `POST /api/v1/accounts/{address}/export` with `archive` over REST, `hmctl privacy export <address> --archive <file>` and `Export-HmAccountArchive` write one .zip on the server's disk; `GET /api/v1/accounts/{address}/export.zip` (the administrator password's alone) and the Deck's "Everything (.zip)" on the account row download the same archive, and `GET /api/v1/me/export.zip` - the "Your data" card on the webmail's Settings page - hands it to the person with no administrator involved. The person's own download is refused (403) to a request authenticated with an app password, or to a webmail session started with one: an app password is a program's credential, and the archive is the whole account. A download is sent from the archive's temporary file a piece at a time, never held in memory whole, and the file is removed once the response is done with it; past 500 MB it is refused with 413 and the operator writes it to disk instead; the disk form has no ceiling but the format's 4 GB. A mailbox whose mail alone is past 2 GB - four times that, which mail does not deflate to as a rule - is refused with 413 before anything is built. Building an archive holds one of the HTTP server's four workers, which serve the webmail and the whole API too, so a download is refused with 409 while an archive of the same account is being built, and with 429 and `Retry-After: 60` while two archives are being built on the server. A large download counts against the listener's cap on large downloads at once (sixteen; one more is answered 503 with Retry-After: 30), and its connection may outlive the listener's five-minute connection limit for as long as its size takes at 128 KB a second.

Inside:

| Entry | What it is |
| --- | --- |
| `manifest.json` | the address, the moment, and the counts of what follows |
| `mail/<folder path>.mbox` | every folder with mail, one mbox each: a `From_` line before each message, body lines beginning `From ` quoted, as the folder download of the self-service API writes them. A folder past 256 MB is written in parts - `<folder path>.mbox`, `<folder path>-part2.mbox` and on, a message larger than that a part of its own - so that no more than one part is held in memory; a name already taken takes ` (2)` before its extension |
| `account.xml` | what the backup carries for the account, in the backup's own form: the settings, rules, fetch accounts, app passwords, sender list, the address book, the calendars, the webmail's preferences, the S/MIME and OpenPGP keys, the files sent as links, scheduled mail - less the credentials, which a backup carries to be restored from and a person's copy has no use for: the password's hash and scheme, the authenticator's seed, the hashes of the app passwords, the recovery codes, the password history and a file's password, a fetch account's password and OAuth token, a browser's push secret, and the wrapped mailbox key of an account encrypted at rest (its mail is in the archive in the clear) |
| `contacts.vcf` | the address book as vCard 3.0, the card a client sent where there is one |
| `calendars/<calendar>/<object>` | every calendar object as the client sent it |
| `preferences.json` | the webmail's preferences as stored |
| `filters.sieve` | the active Sieve script, when there is one |
| `logs.txt` | the lines of the server's own log files that name the address, up to 50 MB. The address is matched whole, without regard to case: the lines of `ann@example.com` are not those of `joann@example.com` nor of `ann@example.com.au` |

`Account.ExportMessages(directory)` and the `directory` form of the POST stay: a directory of `.eml` files mirroring the folder tree, for the operator who wants exactly that.

## Every trace of an address

`Utilities.EraseAddressTraces(address, includeArchive)` over COM, `POST /api/v1/addresses/erase` over REST, `hmctl privacy erase`, `Remove-HmAddressTraces` and the Deck's "Erase traces" on the account row remove what deleting the account deliberately leaves: quarantine entries, message-trace rows, greylisting triplets, distribution-list memberships, aliases on either side, the bounce and complaint records, the rows naming the address in other people's address books (`hm_contacts`) and first-contact memory (`hm_knownsenders`), and the send API's record of what each key sent (`hm_apisends`): the sends the address made go, and it is taken out of the recipients of the rest ([SendApi.md](SendApi.md)). The address is found whatever case a row holds it in - an envelope's `Ann@Example.com` in the message trace, an alias or a list member typed in capitals - on every database, PostgreSQL included, which compares text by its bytes. The certificates a domain's S/MIME authority issued for the address (`hm_smimeissued`, [SmimeAuthority.md](SmimeAuthority.md)) are reached too, differently: a valid one is revoked, and the address, the account and the certificate itself - whose subject is the person's name - are taken off the row, while its serial, fingerprint and revocation stay, because the authority's CRL must go on listing a certificate that is still out there. With the archive included, the person's archive tree is swept file by file and the directories left empty go; and every index row naming the address - as the sender, or as one of the recipients - goes, in whichever mailbox's tree its copy lies. The copies in other people's trees and in the Inbound folder are their mail and are not deleted, so those rows' files stay where they are, no longer in the archive's search nor in an eDiscovery search of the archive, and age out by `ArchiveRetentionDays` as every archived file does; a copy a hold covers keeps its row (below).

The address is matched in any case, on every database: an alias, a list member, a message-trace row or a greylisting triplet that kept `John.Doe@Example.com` as it was typed or as MAIL FROM wrote it goes with an erasure of `john.doe@example.com`. Until 26 September 2026 those four were matched with `=` on the spelling given, which PostgreSQL compares case by case, so there such rows stayed while the erasure reported itself done.

And the stores beside the mailbox, each by its own rule:

| Store | What the erasure does |
| --- | --- |
| Messages held for review (`hm_heldmessages`, [CompromisedAccounts.md](CompromisedAccounts.md)) | A message the address sent, or that would be delivered to it - a recipient as the queue holds it, or as it was addressed, an alias included - is **discarded** as the quarantine's entries are, and as the review page's Discard does: the queue's row, its recipients and its file, then the review row, and the discard fails the erasure (HM7380) if any of them is left. The message itself names the address, and releasing it afterwards would carry the address on. Its other recipients do not get it. The discard is on the application log, by count, and not on the audit trail, whose hash-chained rows would then name the erased address. |
| Messages that expire (`hm_confidential`, [ConfidentialMessages.md](ConfidentialMessages.md)) | The address is **taken out of the recipients** of a message somebody else sent, and out of who opened it, which then reads `[erased]`; the other recipients go on reading it. Each change is made only while the row is still as it was read, and the row is read again after it: a row something else changed at the same moment fails the erasure, which is run again, rather than being written back with the address in it. A message the address sent (its From), or one left with no recipient, is **ended** as a withdrawal ends it: its kept copy deleted, its row removed. The one-time codes and the reading grants the address holds go too. |
| Password-protected messages (`hm_protectedmessages`, [OpenPGP.md](OpenPGP.md)) | A message to the address, and a reply it wrote, is **ended**: the ciphertext deleted, the row removed, under the upload's lock so that a chunk arriving at the same moment cannot put the file back. A message the address's own account sent is **not** reached, unlike a message that expires: its row names its recipient and no sender, the account that owns it is the sender, and its rows go with that account. |
| The recipients an account remembers writing to (`hm_accountrecipients`) | The row goes: in the account's compromised-account baseline the next message to the address is one to a stranger. |
| The out-of-office memory (`hm_autoreplies`, [OutOfOffice.md](OutOfOffice.md)) | The row goes: a reply that is still on answers the address again. |
| Who may book a room or a piece of equipment (`hm_bookingpolicies.bpbookers`, [RoomsAndEquipment.md](RoomsAndEquipment.md)) | The address is **taken out of** every booking policy's list, as it is taken off a distribution list - as written, or through an alias domain's spelling of it; the rest of the list stays. A list the erasure leaves empty would mean everyone in the organisation, which is more than it said, so that policy's automatic answers are **switched off** as well: its delegates answer until an administrator names who may book again. |
| What a room or a piece of equipment remembers of an organiser (`hm_bookinganswers`, the answers it sent them this hour and when its delegates were last told of their request, under the address and under the key requests that named it and were not verified are counted by) | **Deleted**, as the out-of-office memory is: the address is answered again as an organiser the room has not heard from. |
| Whom a room or a piece of equipment accepted a booking from (`hm_bookingdecisions`, the organiser by the booking's UID) | **Deleted**: a delegate's later answer about one of those bookings tells nobody - the delegate tells the organiser themselves. The bookings are calendar objects, and go with the calendars. |
| What the address sent a room or a piece of equipment that waits to be decided (`hm_bookingqueue`, seconds as a rule) | **Deleted**: it is not decided. The message itself is in the room's mailbox, and is reached with the mailboxes. |
| The correspondents' S/MIME certificates and OpenPGP keys other accounts keep (`hm_smimekeys` and `hm_pgpring`, the rows of kind 2) | Removed: a certificate's subject and a key's user id name the person. An account's own certificates and keys are the account's, and go with it. |

Every list of addresses is matched **whole**: `ann@example.com` is not found inside `joann@example.com`, which `LIKE` alone would do, so erasing the one leaves the other's rows as they are - in the quarantine, the send API's record, the archive index and the stores above. Where `LIKE` finds the candidates, an address's own `[` goes into the pattern as `_`, since SQL Server and Compact read `[` as the start of a character class and would never find `ann[1]@example.com` or a domain literal; the whole match decides.

### A legal hold outranks it

An erasure never deletes a message from a mailbox, so a legal hold ([Discovery.md](Discovery.md)) meets it only in the stores it does delete from, and there the hold wins. An archived copy a hold covers - a hold on it, on its account or on its domain - keeps its file and its index row; a message held for review, a message that expires and a password-protected message whose account is held are left exactly as they are. That is not a failure: the REST answer's `held` counts what a hold kept, the application log says it in a line of its own, the Deck's toast says it, and `hmctl privacy erase` prints it, so that whoever answers the person can say what was kept and why. Run the erasure again once the case is closed. COM's `EraseAddressTraces`, and so the Control Panel's "Erase traces...", answers the count removed alone; there the log line is what says a hold kept something, and the confirmation says that what a hold covers is left.

When the holds themselves cannot be read (HM7332), every question is answered "held", which keeps every deletion safe - and what is left then is left for want of an answer, not for a case. The erasure asks whether the holds were read before its first store a hold can keep and again after its last, and if they were not, it **fails**, naming the legal holds as a store to retry (HM6250; `500` over REST), and says nothing about a legal hold. One case is left: an account that cannot be read while some domain is held is answered "held" too, since which domain it is in is the question, and that is counted in `held` though no case may keep it - it needs the account's own row to be unreadable in the moment the erasure reads the others.

eDiscovery's own record is not erased: a case's searches name their custodians in their queries, its holds name what they hold, and its results files and exports under `Discovery\case-<id>` list what was found. That is the record the case exists to keep, and a case is never deleted.

### What it leaves

- **Mail in mailboxes**, the person's own and everybody else's, a mailbox's deleted items, the headers indexed from them (`hm_message_metadata`), and a list's archive of its posts: they are their owners', and go with the message, the account or the list.
- **Other people's calendars** (`hm_calendarobjects`), whose events can name the address as an attendee or the organiser: they are their owners' data, as their mail is, and an event rewritten would be an invitation that no longer says who was invited. Their address books are the exception the erasure has always made, since a contact row is the address and nothing else.
- **Configuration that names the address**: an account's forward, recovery address, verified send-as identities, fetch-account logins and push notification sender filter; a rule's condition or action; a list's moderator, owner or bounce address; the sender allow and block lists, the white list and the blocked senders; a domain's postmaster, report mailbox, protected persons and relay login; a route's addresses and login; a journal rule, an alert rule's recipient and a webhook's address filter. Each is a setting somebody made, and an erasure that rewrote it would change what the server does in a way nobody chose. Aliases and list memberships are the exception, as they always were: they are forwards and deliveries to the person.
- **The audit trail** (`hm_audit`), whose rows are hash-chained: they age out by `audit_retention_days` ([AlertsAndAuditTrail.md](AlertsAndAuditTrail.md)). And the **alert events** (`hm_alertevents`), whose summaries can name an account: the server's record of what it raised, which nothing prunes yet.
- **The spam trap record** (`hm_spamtraphits`) and the sender block a hit made: the evidence of an abuse, kept `SpamTrapHitRetentionDays`, whose clearing is an audited act of its own ([SpamTraps.md](SpamTraps.md)).
- **The delivery queue and the webhook queue**, which drain as they deliver - a message held for review excepted, above.
- **The contacts of the organisations that send DMARC and TLS reports** (`hm_dmarcreports`, `hm_tlsreports`): a reporting organisation's address, not a person's.
- **A mailbox move's journal** (the account's, gone with it) and **a migration job's source login** (the operator's record of the job, gone with the migration).
- **The archive's Inbound folder**, where a copy from outside is filed under its own name and not the address's, and **backups**, which are outside the running server's reach by design.

The logs are the half that is asked for by name: `Utilities.EraseAddressLogLines(address)` over COM, `include_logs` on the REST body, `--logs` and `-IncludeLogs`. Every occurrence of the address in `hmailserver_*.log` and `ERROR_hmailserver_*.log` becomes `[erased]`, so the line says it was changed rather than pretending nothing was there; the count answered is the occurrences rewritten. The address is matched whole, as everywhere in the erasure: `joann@example.com` and `ann@example.com.au` are left as they are when `ann@example.com` is erased, while the address quoted (`'ann@example.com'`, as the lockout and mailing-list lines write it), after `=` (`LOGIN=`, a BATV `prvs=` tag) or after `/` is still the address and is rewritten. The last part of an SRS address (`SRS0=<hash>=<time>=<domain>=ann@forwarder.test`) is not: it is another person's local part at the forwarder's domain, so `ann@forwarder.test` neither erases it nor finds that line in its export. Each file is written beside itself and renamed over the old one, so a crash or a full disk part way through leaves the log as it was. A log past 256 MB is not rewritten in memory and is reported instead - log retention is the answer for it. The Control Panel's account dialog does both halves in one go from "Erase traces...".

The inbound webhooks' queue (`hm_inboundhookqueue`, [InboundWebhooks.md](InboundWebhooks.md)) is swept by the same erasure: every delivery the address sent goes, with the message it kept - a kept one is never swept by age - and the address is taken out of the recipients of the rest, a delivery left naming nobody going with its message.

## What is tested

`API/RestApiPersonExport.cs` (Windows): the archive's entries and counts over COM, the same archive downloaded by the operator and by the person, the key refused, and an erasure reaching the other person's address book, the first-contact memory and the log. `API/RestApiArchive.cs`: the held copy that survives the sweep, counted once in `held` for its file and its row together. `Infrastructure/PrivacyTools.cs`: the `.eml` export and the stores the erasure has always reached, and an alias, a list member and a greylisting sender kept in mixed case found by an erasure in lower case (a test of the old code's defect on PostgreSQL only, since the other databases matched them under their collations). `Infrastructure/ArchiveIndexTests.cs`: the archive rows of a longer address kept by an erasure of the shorter one, and an address with an underscore in it, which an envelope wrote in capitals, found.

`API/RestApiErasureStores.cs` (REST port 10160): a message held for review discarded - its queue row and its queue file gone - when the address is a recipient, when it sent it, and when an alias of it is what the message was addressed to, which only the queue's recipient rows say; the sending account's memory of the address gone; a message that expires losing the address from its recipients and from who opened it and still read by its other recipient, one sent to the address alone and one it sent ended with their kept copies, the address's one-time code forgotten, and an address with a `[` in it found; a password-protected message to it ended with its ciphertext, and the reply it wrote with its own, while one its own account sent is not reached; a correspondent's S/MIME certificate and OpenPGP key removed beside another correspondent's that stay, and the address's own certificate and key (kind 1) kept; an out-of-office reply answering the address again - each beside an erasure of `ann...` that leaves `joann...` alone; and a legal hold on the sending account keeping its held message, its message that expires and its password-protected one, counted in `held` and said in the application log, until the case is closed. The Deck's harness drives the row's link, the confirmation that names the stores and the toast that says what a hold kept; the webmail's harness finds the card's link.

Not proved by a test, and read in the code instead: the erasure failing when the holds cannot be read (a failed read of `hm_discoveryholds` cannot be made on the bench without breaking every other fixture's holds); a discard that leaves the queue file or the recipient rows, and so HM7380; a kept copy or ciphertext that cannot be deleted leaving its row withdrawn and the erasure failed; two erasures of one message's recipients at the same moment, and an opening recorded in between; a chunk of a password-protected upload racing the erasure; a message held for review whose recipients run past the 2,000 characters of its review row (the alias case goes the same way, through the queue's recipient rows); and the erasure's `LIKE` on MySQL and PostgreSQL, since the bench runs one database.
